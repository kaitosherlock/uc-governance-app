## The lifecycle you are implementing

    Validate -> Authorize -> Build plan -> Preview -> Confirm -> Revalidate -> Execute -> Verify -> Audit

Build it under `backend/app/mutations/`:

1. **Plan builder.** Takes a `PlanCreateRequest` plus the resolved actor, and produces a `Plan`.
   It binds, and the built plan must carry: the authenticated actor, the execution identity, the
   workspace id, the targets, the normalized changes, the relevant observed current state, and an
   expiry. Preview is read-only: building a plan must never call a write path.

2. **Integrity token.** The plan a client sends back must be provably the plan the server built.
   Use HMAC-SHA256 over a canonical, deterministic serialization of the binding fields, with a
   secret read from settings — add it to the settings module in the established style and to
   .env.example. Never log it, never return it in a response, never include it in an error. In
   fixture mode a development default is acceptable; in connected mode a missing or short secret
   must fail closed at startup with a clear message, exactly like the existing mode guard does.
   Constant-time comparison only. A tampered token is `PLAN_INVALIDATED`, not a 500.

3. **TTL.** `expires_at` on the plan; executing after it is `PLAN_EXPIRED`. Use timezone-aware UTC
   throughout. Put the TTL in settings with a documented default; do not hardcode it at the call site.

4. **Observed state hash.** Hash the state the plan was previewed against. At execute time, re-read
   that state and compare. A difference is `PLAN_STALE` and the response must carry `next_steps`
   telling the user to regenerate the preview. This is the whole point of the revalidate step, so
   it must be a real re-read through the adapter, not a cached value from the build.

5. **Executor.** Applies a plan through the adapter layer, per target. Multi-target execution is
   NOT atomic and must not pretend to be: report `TargetOutcome` per target and derive the overall
   `OperationStatus` from them (all applied -> `applied`; some applied -> `partially_applied`; none
   applied -> `failed`). An ambiguous result — timeout, dropped connection, any case where you
   cannot tell whether the change took effect — is `unknown`, never `failed`. Never retry an
   ambiguous mutation anywhere in the engine or in middleware.

6. **Verifier.** After execution, read supported state back and record whether each target was
   actually verified. `TargetOutcome.verified` must mean "I read it back and saw it", not "the call
   returned 200". Where read-back is not supported, say so honestly rather than claiming verified.

7. **Operation store.** A `Protocol` plus an in-memory implementation, following the same pattern
   the read adapters already use. It records operations durably enough to answer `getOperation` and
   to support `reconcileOperation`, which re-reads current state for an `unknown` operation and
   resolves it. Idempotency: a duplicate submission of the same plan must return the existing
   operation with `DUPLICATE_OPERATION`, not execute twice. Nothing may be auto-replayed after a
   restart.

8. **Routes** in `backend/app/api/v1/routes_plans.py`, wired into the app exactly as
   `routes_reads.py` is, implementing the five frozen operations with the frozen envelope. HTTP 202
   is returned when and only when the operation status is `unknown`.

9. **Plan kind registry.** Plan kinds register into the engine. This task registers NONE of them;
   P1-05 does. A request for an unregistered kind returns `NOT_IMPLEMENTED` with the honest reason.
   That is a truthful response about work not yet done, not a placeholder — do not stub a kind that
   returns success without executing, and do not fabricate an impact analysis.

10. **Authorization and audit.** Authorize at build AND again at revalidate, through the existing
    authz module. Emit an audit record at each lifecycle boundary using the existing redaction-aware
    logging, carrying the correlation id. No secret, token, or raw SDK exception may reach a log or
    a response.

11. **Capability registry.** Update the entries this task makes real, and leave the rest honest.

## Tests

Under `backend/tests/`, covering at minimum: a tampered token is rejected; an expired plan is
rejected; a changed observed state produces `PLAN_STALE`; partial multi-target execution reports
per-target outcomes and `partially_applied`; an ambiguous execution produces `unknown` and is NOT
reported as failed; reconcile resolves an `unknown` operation; a duplicate execute returns the
existing operation rather than executing twice; preview performs no write; an unregistered kind
returns `NOT_IMPLEMENTED`. Use the existing fixture adapters; do not reach the network.
