### The requirement that matters most here

**Secret material must never leave this application.** The contract says so in the response
description: "Secret material is never included." A storage credential wraps a cloud identity, and
the SDK objects in this area can carry role ARNs, client ids, access-connector ids, and in some
shapes a secret or token field.

Map by **explicit allowlist** — construct the DTO field by field from the nine names above — never by
iterating the SDK object, never by `**asdict(...)`, never by copying unknown keys into a `raw` bag.

Then add a test that proves it: build an SDK-shaped object carrying an obviously secret-looking extra
field, map it, and assert that field appears nowhere in the serialized response. A test that only
checks the expected fields are present would pass while a secret leaked alongside them.

### `allowed_actions` must not advertise what cannot be done

Every entry you emit must be truthful. Since the contract exposes no mutation route for these
securables, the honest answer for mutating actions is `allowed: false` with a `reason_code` from the
closed enum at line 1351 and a `reason` a person can act on. `NOT_IMPLEMENTED` is the right code for
"this application has not built it"; `UNSUPPORTED_FOR_TYPE` for "this does not apply to this kind of
object". Use `MODE_READ_ONLY` in `connected_readonly`, consistently with the existing adapters.

`PlanKind` has a `delete_asset` member. **Do not stretch it to cover a storage credential or an
external location** on the strength of the name alone. If section 7.6 does not say it applies, report
`delete` as not allowed with a reason and record the ambiguity rather than wiring it up.

### The IAM-versus-UC distinction, in the copy

This is the substantive governance point of the task, so put it in `meta.limitations` on both reads
rather than only in a doc.

A storage credential existing in Unity Catalog, and a caller being able to see it, says nothing about
whether the underlying cloud IAM role, managed identity or service account actually grants access to
the bucket. That is configured outside Unity Catalog, in the cloud provider, and **this application
cannot see it and has not checked it**. Someone reading a green-looking list must not conclude that
storage access works. Say that plainly.

Likewise `read_only` and `isolation_mode` are Unity Catalog's own declarations, not an observation of
effective cloud permissions.
