## 1. Authorization, per route

For **every** route the application exposes, assert what each role may and may not do. Drive this
from the route table rather than hand-listing a few, so a route added later without an authorization
decision shows up as a failure rather than slipping through unnoticed. A reader must not be able to
create or execute a plan. An approver's authority must be bounded by scope, not merely by role name.

## 2. Identity, adversarially

- A request with **no** `x-forwarded-access-token` is `UNAUTHENTICATED`, in every connected mode.
- Forged or contradictory forwarded headers do not change who the actor is. Specifically: a request
  whose token verifies as user A but whose `X-Forwarded-Email` claims user B is rejected, and the
  rejection names neither address.
- A token that verifies as a **service principal** rather than a user does not satisfy the
  user-identity requirement.
- The actor and the executor are distinct in `/me`, and the executor is never silently substituted
  for the actor when authorizing.
- No identity value, token or secret appears in any error body or any log record on any of these
  paths. Assert this by inspecting captured log output, not by reading the code.

## 3. Plan lifecycle, through HTTP

The unit tests already cover the engine. These must go through the API:

- A plan built by actor A cannot be executed by actor B.
- A plan's integrity token cannot be replaced, truncated or omitted.
- An expired plan is `PLAN_EXPIRED`; a plan whose observed state moved is `PLAN_STALE`; a tampered
  one is `PLAN_INVALIDATED`. Each with its correct HTTP status from `ERROR_HTTP_STATUS`.
- Executing the same plan twice returns the existing operation with `DUPLICATE_OPERATION` and does
  not execute a second time.
- An ambiguous execution returns **HTTP 202** with `Operation.status == "unknown"`, and 202 is
  returned in no other circumstance.
- `reconcile` on an `unknown` operation resolves it by reading current state, and does not re-run
  the write.
- An unregistered plan kind is `NOT_IMPLEMENTED`, not a 500 and not a silent success.

## 4. Degraded modes

- In `connected_readonly`, every mutation route returns `MODE_READ_ONLY` **before** touching any
  write path. Prove the ordering, not just the status code: a read-only deployment must not reach
  the adapter at all.
- With Lakebase unconfigured, the features that depend on it are `NOT_CONFIGURED` with usable
  `next_steps`, and the rest of the application still works.
- Fixture mode cannot start when `DATABRICKS_APP_PORT` or `DATABRICKS_CLIENT_ID` is present, so a
  deployed app can never serve synthetic data as though it were real.
- A connected mode refuses to start with a `UCGOV_PLAN_HMAC_KEY` under 32 characters.
- When an upstream call fails, the client sees the mapped contract error and never a raw SDK
  exception, a stack trace or an internal path.

## 5. Envelope invariants

Assert across the whole surface, generically: no failure is ever returned with HTTP 200; every error
body carries `success: false`, a `code` from the frozen enum, a `message` and a `correlation_id`; an
inbound `X-Request-Id` is echoed into `meta.correlation_id`; an unknown path is `NOT_FOUND` rather
than an HTML page.
