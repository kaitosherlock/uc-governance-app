## Step 1. Write `backend/app/tools/introspect_sdk.py`

A CLI that imports `databricks.sdk.WorkspaceClient` and `AccountClient` **without constructing
them** (constructing would need credentials) and reports, for a list of candidate operations:

- whether the service attribute exists on the client class,
- whether the named method exists on that service class,
- the method's exact signature parameter names,
- for the DTO returned, the declared dataclass field names where they can be read statically.

Use `typing.get_type_hints`, `inspect.signature` and the classes reachable from
`databricks.sdk.service.*`. Do not instantiate a client. Print a machine-readable JSON report and
support `--json <path>` to write it.

Cover at minimum these service attributes, all of which are confirmed present:
catalogs, schemas, tables, grants, volumes, functions, registered_models, model_versions,
metastores, storage_credentials, external_locations, connections, shares, recipients, providers,
workspace_bindings, quality_monitors, serving_endpoints, statement_execution, users, groups,
service_principals, current_user.

Also probe, and report honestly as present or absent, these uncertain surfaces that the matrix
seed lists as `unknown`: entity_tag_assignments, tag_policies, policies, rfa, external_lineage,
external_metadata, clean_rooms, credentials, temporary_table_credentials, resource_quotas.

## Step 3. Write `backend/tests/contract/test_sdk_shapes.py`

A pytest module that asserts, for every operation the application will actually call, that the
service attribute and method still exist on the installed SDK and that the parameter names the
adapters will use are present in the signature. This is the guard that a future SDK bump cannot
silently break the adapters. Mark it clearly as a mocked contract test, not live evidence.

Keep it data-driven: a module-level list of `(service, method, required_params)` tuples and one
parametrized test, so adding a row is a one-line change.
