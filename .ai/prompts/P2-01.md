## Part 1 — the two read endpoints

Neither exists yet. `routes_reads.py` currently serves eight paths and neither of these is among
them.

**`GET /assets/{securable_type}/{full_name}/tags` → `TagsResponse`.**
- Object-level tags in `data.tags`, column-level tags in `data.column_tags` keyed by column name.
- A column with no tags does not need a key; do not emit empty arrays as filler.
- Every `Tag` carries honest `allowed_actions` through `ReadPolicy.tag()`. A `system` tag comes
  back with its editing actions refused and the reason attached.
- A securable type that cannot carry column tags returns an empty `column_tags` map, not an error.

**`GET /tag-policies` → `TagPolicyListResponse`**, paginated with the existing `PageToken` and
`PageSize` parameters and the existing `Page` envelope.
- `allowed_values` is nullable. A governed tag with an open value set has `null` here, which is
  different from `[]` meaning "no value is permitted". Preserve that distinction; do not collapse
  null into an empty list.
- `allowed_actions` on a policy reflects whether this actor may assign that governed tag. If the
  app cannot determine tag-assignment authority — and per the capability matrix it cannot, see
  Part 3 — the action is refused with a reason that says the authority is unknown, never allowed
  by default.

## Part 2 — the two plan kinds

Register `assign_tags` and `remove_tags`, and only those two. The other fifteen unregistered
`PlanKind` values must keep returning `NOT_IMPLEMENTED`; prove that with a test.

`TagChanges` carries an optional `column`. When `column` is present the change targets that
column's tags; when absent it targets the object. One plan is either object-level or column-level,
not both.

**Refusals that are correctness requirements, not niceties:**

- **A system tag can never be assigned or removed.** Route the decision through the same
  `ReadPolicy.tag()` result the read path uses, so the preview's refusal and the table's disabled
  button always agree.
- **A governed tag whose value is outside its policy's `allowed_values` is a validation error**
  naming the key, the rejected value and the permitted set. When `allowed_values` is `null` any
  value is permitted; do not reject on an open set.
- **A tag already present with the same value is a no-op** and must be previewed as one rather
  than counted as a change, the same way P1-05 handles an already-held privilege. Same for
  removing a tag that is not there.
- **Assigning a key that already exists with a different value is an overwrite, not an addition.**
  The preview's `description` must say the old value is being replaced and name it. Silently
  overwriting a governed tag's value is exactly the kind of change a reviewer must see.

**`impact.unknown` must carry the ABAC consequence.** Section 7.3 requires that possible ABAC
consequences of a tag change be explained. This app cannot evaluate Databricks ABAC policies, so
the honest answer is not silence and not a guess: every assign or remove whose key could
participate in a policy predicate states in `impact.unknown` that row filters, column masks or
ABAC policies keyed on this tag may begin or cease to apply, and that the app has not evaluated
them. A PII tag does not prove masking is active, and the preview must not imply that it does.

Everything P1-05 requires of a plan kind applies here unchanged: `statement_preview` on every
`NormalizedChange` with identifiers quoted through the existing `_json` helper so a crafted tag
key or value cannot alter the statement; `description` as the prominent human sentence;
`prerequisite_notes` where a prerequisite exists; observe before and verify after through the
handler's `observe` and `verify`, returning the honest "cannot verify" signal rather than `True`
when read-back cannot confirm; and no transaction illusion over multi-target execution.

**Mode.** This deployment runs `connected_readonly`. Registering these two kinds must not make a
read-only deployment writable — add both to `register_connected_readonly_plan_kinds` so the
engine's guard returns `MODE_READ_ONLY` rather than `NOT_IMPLEMENTED`, and test it.
